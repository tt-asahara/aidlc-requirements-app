# M7 許可の中継 UI

M4 の owner 認可付き API に許可カードを接続した。ルールの生成・対象コマンドの判定・判断の監査はサーバーが行い、UI からルールを入力・拡大する機能は持たない。

- 各ターンの直後に、ツール名、コマンド全文、拒否元のターン ID、警告、判断者と時刻を表示する。未読の古い履歴に属する要求も会話ペインから操作できる。
- 許可・拒否・取消は専用 API だけに POST する。許可時に turn / reconnect API を呼ばず、空の入力欄に続行文の下書きだけを入れる。
- 編集中の返答を自動で置き換えない。「続行文を入力欄へ入れる」を押した場合だけ明示的に置き換える。実行は別の送信ボタンで行う。
- 下書きの作成元を owner / project / request ごとに保持する。取消は、その要求から生成した未編集の下書きだけを消す。手入力・編集済みの返答は保持する。
- 追加許可の一覧から取消できる。取消は次のターンから適用され、既に実行中の処理を止めるには別の中止操作を使う。
- 同じ要求の操作を同期ロックで重複送信しない。移動中に応答が返っても、元の owner / project の cache と下書きだけを更新する。再読込や GET の再取得から送信・許可判断を起こさない。
- 非互換の実行モードは閲覧だけとする。認可失敗時は cached permission card を隠す。サーバーの所有者検査は変更していない。

## 許可表現の制限

計画修正 PR #9 の決定に従い、単純な完全一致の Bash コマンドだけを許可できる。
ワイルドカード、引用・展開・シェル演算子、非 Bash の入力限定ができない要求は、証跡を表示し、許可ボタンを無効にする。サーバーでも approve は 422 となる。
CLI の複雑な入力の照合や実モデルでの再確認は、価格・請求照合待ちのため実施していない。広いルールへの置換や上流設定への追加は行っていない。

## 検証

Mac / Bun 1.3.14: lint、strict 型検査、137 テスト / 476 assertions、Web build を確認。
Playwright は既存の会話・移動・SSE・中止・成果物の6ケースと、以下の3ケースで9 E2Eを確認した。

1. 拒否結果 → wildcard の許可不可 / 削除警告 → 拒否 → git status の許可 → 未送信下書き → 利用者の送信 → refined-mockups 完了表示。
   許可ボタンを連打しても判断は1回だけで、送信するまでターン数は3のまま。監査情報と追加ルールの一覧も確認する。
2. 拒否 → 利用者が再送 → 許可 → 取消で生成下書きだけを削除。さらに利用者が再送し、編集済み下書きは許可・一覧からの取消後も保持する。
   再読込ではターンを追加しない。
3. 許可の応答を遅らせて別プロジェクトへ移動し、応答が別の入力欄へ混ざらないこと、元のプロジェクトだけに下書きがあることを確認する。
   他 owner の permission API は404、UIに他人のカードを表示しない。

単体テストでも I1 / I5 の下書き保持と取消の出所を検証する。既存 API / queue テストは、次ターンの allowedTools に承認済みルールが入り、取消後に消えることを確認している。
合成ログの git status / echo *.md / rm -rf ./fixture-trash は拒否のメタデータだけで、シェルで実行しない。使い捨てデータ・ブラウザプロファイルだけを使い、追加のモデル呼び出しはない。
